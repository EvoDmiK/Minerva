# 임베딩 API 내부망 직접 호출

## 요약

NAS의 RobinGraph가 Mac mini의 Jina 임베딩 서버를 공개 주소(`https://embed.dove-nest.com`)로 호출하고 있었다. 같은 집 안의 서버인데도 요청이 Cloudflare 홍콩(HKG) 데이터센터를 왕복해 호출마다 0.4~0.6초가 더해졌다. NAS 배포 설정만 Mac mini 내부망 주소로 바꿔 호출 시간을 약 4분의 1로 줄였다.

| 경로 | 질문 1건 임베딩 |
| --- | --- |
| 변경 전: NAS → Cloudflare(HKG) → NAS NPM → Mac mini | 0.79초 (중앙값), 최소 0.57초 |
| 변경 후: NAS → Mac mini 내부망 | 0.20~0.23초 |

임베딩 계산 자체는 약 0.2초이고, 나머지는 경로 비용이었다. 검색 답변이 질문마다 약 0.5초 늦어지고, 대량 적재에서는 호출 수만큼 쌓인다(1,000회면 약 8~10분).

## 왜 처음부터 공개 주소였나

- 임베딩 기능을 처음 추가한 커밋부터 `.env.example` 기본값이 공개 주소였다.
- NAS 배포 준비 때 같은 값을 `.env.nas.example`과 배포 문서로 옮겼다.
- 개발 초기에는 노트북·다른 서버 어디서든 같은 주소로 쓰고, HTTPS로 API 키를 보호하는 공개 주소가 편했다.
- 임베딩 서버도 처음부터 "외부 노출" LaunchAgent 서비스로 만들어졌다.
- 기술적 제약이 아니라 편의상 시작한 설정이 NAS 배포까지 그대로 남은 것이다. PostgreSQL은 이미 내부 IP를 쓰고 있었다.

## 인증서와 경로는 별개

인증서를 Let's Encrypt로 바꿔도 Cloudflare 프록시가 켜져 있으면 똑같이 홍콩을 거친다. 경로는 DNS가 어디를 가리키느냐(프록시 여부)로 정해지고, 인증서는 그 경로의 암호화와 서버 확인만 맡는다.

| 설정 | DNS가 가리키는 곳 | 경로 |
| --- | --- | --- |
| Cloudflare 프록시 켬 | Cloudflare | 홍콩 경유 |
| DNS only | 집 공인 IP | 직접 (공인 인증서 필요) |
| 내부 IP 직접 호출 | DNS 사용 안 함 | Mac mini로 바로 |

## 변경

| 파일 | 내용 |
| --- | --- |
| `.env.nas.prod`, `.env.nas.test` | `ROBINGRAPH_JINA_ENDPOINT`를 Mac mini 내부망 `:8765/v1/embeddings`로 변경 |
| `.env.nas.example` | 같은 값과 이유 주석 |
| `docs/nas-deployment.md` | 내부망 호출 이유, 측정값, healthz 확인 명령 갱신 |
| `.env.example` (개발용) | 공개 주소 유지 |

- 내부망 구간은 HTTP라 API 키가 집 내부망에서만 평문으로 오간다.
- Mac mini IP가 바뀌면 안 된다. NPM도 같은 IP를 쓰고 있다.

## 적용 방식

- `deploy_nas.sh deploy`·`update`는 이미지를 다시 빌드한다. 작업 폴더에 커밋되지 않은 코드가 있어 빌드하면 그 코드가 운영에 섞인다.
- 그래서 실행 중인 이미지와 태그가 같은지 확인한 뒤, 같은 이미지로 `docker compose up -d --no-build api`를 실행해 설정만 바꿔 컨테이너를 다시 만들었다.
- 배포 스크립트가 쓰는 대상별 값(`ROBINGRAPH_COMPOSE_PROJECT`, `ROBINGRAPH_API_CONTAINER`, `ROBINGRAPH_IMAGE` 등)을 직접 지정했다.
- test에 먼저 적용해 확인한 뒤 prod에 적용했다.

## 검증

| 항목 | test | prod |
| --- | --- | --- |
| 컨테이너 health | healthy | healthy |
| `deploy_nas.sh verify` | 통과 (`deployment_target: test`) | 통과 (`deployment_target: prod`) |
| 앱 임베딩 클라이언트 `embed_query` | 512차원, 0.20초 | 512차원, 0.23초 |
| 32개 묶음 `embed_documents` | 1.39초 | 0.97초 |
| 임베딩 서버 healthz (내부망) | — | `ready`, `mps`, `float16` |
| 공개 사이트 | — | 200 |

prod `/health`의 `taxonomy_release: unknown`은 Neo4j 데이터에서 읽는 값이라 이번 변경과 관계없다.

## 트러블슈팅 메모

- 측정 스크립트가 공개 주소에서 403을 받았다. Cloudflare가 기본 User-Agent `Python-urllib`를 봇으로 막은 것이다. RobinGraph는 `RobinGraph/0.1`을 보내 영향이 없었다. 공개 주소로 urllib를 쓸 때는 User-Agent를 지정해야 한다.
- 작업 중 Mac mini 쪽 Codex가 같은 NAS 폴더를 동시에 수정하고 있었다. 수정된 파일 옆에 macOS가 만드는 `._` 부속 파일이 보이면 Mac에서 네트워크 공유로 편집 중이라는 뜻이다.
- Codex가 `.env.nas.*`를 백업(`*.rg001-backup-*`)한 뒤 MLflow 트레이싱 변수를 추가했지만, 바꾼 임베딩 주소는 유지됐다. 실행 중인 컨테이너에는 MLflow 변수가 아직 반영되지 않았다.

## 상세 보완 — 2026-10-05

### 측정 결과를 재사용할 때의 기준

0.79초와 0.20~0.23초는 당시 질문 임베딩 호출의 관측값이다. 전체 채팅 응답은 의도 판별·DB 조회·문헌 답변 생성·사진 등 다른 단계도 포함하므로, 임베딩 개선 비율을 전체 응답의 개선 비율로 그대로 적용하지 않는다.

| 검증 | 확인한 사실 |
|---|---|
| embed_query | 같은 애플리케이션 클라이언트가 512차원 결과를 받음 |
| embed_documents | 32개 묶음 요청의 반환과 소요 시간 확인 |
| healthz | 해당 시점 서버 준비 상태·가속 장치·정밀도 확인 |
| API health | TEST·PROD 프로세스의 정상 상태 확인 |

같은 모델·차원·입력 조건으로 경로만 바꿔 비교해야 경로 비용을 해석할 수 있다. 문서 묶음 호출 시간은 질문 한 건 호출 시간과 따로 기록한다.

### 설정 변경과 코드 배포의 차이

이 작업에서는 실행 중인 이미지를 유지하고 설정만 반영해 컨테이너를 재생성했다. 새 코드·의존성·정적 파일이 필요한 변경은 별도 빌드·배포가 필요하다. 반대로 내부 endpoint 주소만 바뀐 경우에도 실행 중인 컨테이너가 새 값을 받았는지 실제 호출로 확인해야 한다.

내부 IP와 포트의 접근 가능성, 임베딩 차원, 응답 성공을 확인하되 API 키나 전체 환경 파일을 문서에 복사하지 않는다. IP가 바뀌면 연결 설정과 NPM의 대상도 함께 대조한다.

### 후속 기록과 미확인 항목

원문 ‘남은 일’의 커밋·백업 정리 상태는 이번 문서 보완에서 재확인하지 않았다. 근거 없이 완료 표시하지 않는다. MLflow 변수의 당시 미반영 상태와 이후 RG-001 추적 검증 완료는 서로 다른 시점이며 현재 상태는 [[Work/RobinGraph/RobinGraph 작업 백로그|작업 백로그]]를 따른다.
