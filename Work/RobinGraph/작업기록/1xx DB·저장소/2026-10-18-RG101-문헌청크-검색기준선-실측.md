# RG-101 문헌 Chunk 검색 기준선 실측 — 2026-10-18

[[Work/RobinGraph/작업기록/1xx DB·저장소/작업 백로그|1xx DB·저장소 작업 백로그]] · [[Work/RobinGraph/RobinGraph 작업 백로그|전체 작업 백로그]]

## 요청 배경·목표·작업 범위

사용자가 백로그의 착수 대기 작업이었던 RG-101의 첫 단계 진행을 승인했다. 이번 작업의 목표는 TEST 환경에서 읽기 전용으로 문헌 청크 규모, 전문·벡터·하이브리드 검색 지연(p50/p95), 정책 필터 탈락률 및 서버 메모리 지표를 실측하여 PostgreSQL(pgvector) 분리의 필요성을 판단하는 기준선을 확보하는 것이다.

- **주의**: 이번 작업은 전체 RG-101의 완료가 아니며, PostgreSQL 분리 구현, DB 스키마 DDL/쓰기, 재색인, 대량 수집, 배포 승인을 포함하지 않는다.
- 종 이름 벡터 검색(`robingraphTaxonNameVector`)은 Neo4j에 그대로 유지되며 이 작업의 문헌 청크 분리 대상과 구별한다.

## 확인한 현재 상태 (Fixture 코퍼스)

실행 중인 TEST 앱은 M4 16GB Mac(`192.168.219.97:8000`)의 `robingraph-api-test`이며, Neo4j는 32GB Mac(`bolt://192.168.219.98:7687`), PostgreSQL은 NAS(`192.168.219.99:5433` `robingraph_test`)다. 스크립트에서 target과 Neo4j URI를 강제 확인하고, PostgreSQL DB도 일치할 때만 조회했다.

- **Document**: 2개 (모두 `RobinGraph` 및 `Fixture` 라벨).
- **Chunk / HybridSearchChunk**: 4개.
- **본문 크기**: 총 171문자, UTF-8 합계 357바이트 (본문 payload 문자열 합계이며, DB 인덱스나 레코드 크기가 아님).
- **HybridVectorChunk**: 2개, 512차원 벡터 (총 벡터 성분 1,024개. 원소 수를 실제 인덱스 메모리로 직접 환산하지 않음).
- **인덱스 상태**: Chunk 전문 인덱스(`robingraphChunkFulltext`) 및 벡터 인덱스(`robingraphChunkVector`) 모두 ONLINE 100%. 별도 종 이름 인덱스(`robingraphTaxonNameVector`)도 ONLINE 유지.
- **도메인 그래프 노드**: SourceDataset 3개, Taxon 33,694개 (도메인 분류 노드 수를 문헌 코퍼스 규모로 간주하지 않음).
- **자료 성격**: 2026-10-15의 RG-202 문헌 감사와 동일한 소규모 Fixture 자료이며, 실제 방대한 다문헌 코퍼스에서의 측정이 아님을 명시한다.

## 구현과 재현

새로 추가된 `scripts/measure_chunk_search.py`는 순수 읽기 전용 TEST 계측 스크립트다.
- `bootstrap_index_chunks`, DDL, 쓰기 트랜잭션, 적재 함수를 전혀 호출하지 않는다.
- 기존 프로덕션 검색 코드를 변경하지 않고 동일한 `Neo4jHybridSearch.search` 및 내부 쿼리(`_RECHECK_AND_CITE_QUERY`)를 그대로 활용한다.
- 집계 수치, 지연 통계, 오류 타입만 출력하며 문헌 본문, 벡터 데이터, 비밀번호는 결과물로 내보내지 않는다.
- PostgreSQL 조회 시 `default_transaction_read_only=on`과 `statement_timeout`을 설정해 metadata만 안전하게 조회했다.
- 계측 보조 스크립트(`inventory.py`, `memory.py`)는 `docs/verification/assets/2026-10-18-rg101/`에 함께 보존했다.

```sh
# 실행 재현 명령 (컨테이너 내부 읽기 전용 실행)
docker --context orbstack exec -i robingraph-api-test python - < scripts/measure_chunk_search.py
uv run --locked --extra test python -m unittest tests.test_chunk_search_measurement
graphify update .
```

## 측정 설계와 실제 결과

기존 `data/eval/v1/search-questions.jsonl`의 5개 fixture 질의를 사용했다.
- **임베딩 지연 분리**: 실제 설정된 임베딩 서비스(Jina API)에 5회 요청하여 각 질의의 512차원 벡터를 1회씩 먼저 생성한 뒤, DB 측정 시에는 생성된 벡터를 메모리에서 재사용하여 순수 DB 검색 시간에서 외부 네트워크/임베딩 시간을 분리했다 (합성 벡터나 mock API가 아님).
- **측정 방식**: 모드별 1회 전체 질의 warmup을 실행한 뒤, 10회 반복 × 5질의 = **모드별 50표본**을 측정했다 (concurrency 1, warm sequential baseline). 부하/스케일 테스트가 아니다.
- p50은 중앙값(median), p95는 nearest-rank 방식으로 계산했다.

### DB 검색 경로별 지연 (50표본)

| 검색 경로 | 표본 수 | p50 (ms) | p95 (ms) | 최대 (ms) |
|---|---:|---:|---:|---:|
| 전문 검색 전체 | 50 | 3.945 | 6.806 | 11.232 |
| 벡터 검색 전체 | 50 | 8.920 | 18.262 | 20.909 |
| 하이브리드 전체 | 50 | 9.504 | 10.851 | 25.447 |
| 전문 쿼리 단계 | 50 | 1.910 | 2.643 | 5.691 |
| 벡터 쿼리 단계 | 50 | 4.358 | 4.612 | 4.631 |
| 정책 재확인 단계 | 50 | 1.862 | 2.383 | 3.286 |

- 검색 전체 시간은 클라이언트 로직, Bolt 드라이버 왕복, 정책 재확인 쿼리, RRF 결합을 포함하며, 외부 임베딩 생성 및 LLM 답변 생성 시간은 포함하지 않는다.
- 벡터 p95(18.262ms)가 하이브리드 p95(10.851ms)보다 높게 나온 것은 실행 순서와 런타임 변동이 통제되지 않은 별도 50표본 측정의 변동이며, 하이브리드가 더 빠르다는 일반적 기술 결론으로 해석하지 않는다.

### 외부 임베딩 API 실측 지연
- 5개 질의에 대한 실제 Jina 임베딩 호출 시간:
  - 1번째 질의: **8,729.422 ms**
  - 2~5번째 질의: **215.594 ms, 216.448 ms, 215.484 ms, 205.979 ms**
- 첫 호출과 이후 호출 간 큰 차이가 관측되었으나, 모델 cold-start, 네트워크 레이턴시 등 세부 원인을 분리 검증하지는 않았다.

### 정책 필터 동작
- 130회분 후보 합집합 중 정책 재확인 탈락 0건, eligible embedding 불허 0건, fixture 금지 ID 반환 0건.
- 현재 후보에 실제 불허 항목이 없으므로, 이는 정책 취소나 fail-closed 경계에 대한 실제 부정(negative) 사례 검증 완료를 뜻하지 않는다.

## 메모리 및 PG 인프라 확인

- **Neo4j 32GB Mac 서버 환경**:
  - JVM 설정: Heap initial 4GiB / max 6GiB, page cache 설정 1GiB.
  - JMX Heap used: 계측 전 1,068,029,448 B (~1.00 GiB) → 계측 후 1,411,962,376 B (~1.32 GiB). Non-heap used: 전 266 MB → 후 276 MB.
  - 다중 용도로 공유되는 인스턴스이며 백그라운드 GC 및 타 요청을 통제하지 않았으므로, 이 힙 변화량을 청크/벡터의 메모리 점유량으로 귀속할 수 없다.
  - JMX에 page-cache 관련 MBean이 노출되지 않아 page-cache hit ratio, 프로세스 RSS, 인덱스 디스크 파일 크기는 **미측정**이다 (32GB Mac에 대한 BatchMode SSH 접속이 거부되어 docker stats 접근 불가).
- **NAS PostgreSQL (`robingraph_test`) 인프라 확인**:
  - `pg_available_extensions` 메타데이터 조회:
    - `pg_trgm` (1.6)은 available 상태이나 `installed_version`은 `null` (설치 가능하나 미설치).
    - `vector` (pgvector), `pg_bigm`, `pgroonga`는 현재 인스턴스 사용 가능 확장 목록에 전혀 존재하지 않음.
  - 현재 NAS PostgreSQL 컨테이너(`postgres:16-alpine`, n8n 공유)에는 pgvector가 없음을 확인했다. 확장을 강제 설치하거나 DB 이미지를 교체하지 않았다.

## 판단과 후속 과제

- **현재 판단: Neo4j 청크 저장소 유지, PostgreSQL 분리 구현 보류**:
  - 현재 Fixture 코퍼스는 4개 청크(357바이트)에 불과하여 규모 증가로 인한 병목 현상을 재현할 수 없었고, pgvector와의 실제 대조군 비교도 수행하지 못했다.
  - 외부 임베딩 지연(~210ms / 첫 호출 8.7s)이 DB 검색 지연(~4~10ms)보다 훨씬 크게 관측되었으나, 이를 전체 시스템 병목으로 단정하지 않는다. 검색 백엔드를 PG로 바꾼다고 해서 외부 임베딩 지연이 해결되는 것은 아니다.
- **RG-101 진행 상태**:
  - 전체 완료가 아니며, **착수 · 소규모 기준선 측정 완료, 실제 문헌 규모 판단 후속** 상태로 갱신한다.
  - 향후 대표 문헌 코퍼스와 한국어 질의 세트, 정확도 및 지연 품질 목표를 먼저 확정한 뒤, 격리된 환경에서 코퍼스 규모별(예: 1천, 1만, 10만 청크) 지연 및 메모리를 측정해야 한다.
  - 아울러 pgvector를 지원하는 별도 PostgreSQL 인프라 후보 검토와 한국어 전문 검색(`pg_trgm` vs `pg_bigm` 등) 품질 비교가 선행되어야 한다.
- **ADR-0007 상태**:
  - `docs/decisions/0007-chunk-search-store-split.md`는 **Proposed** 상태를 유지하며 실측 후속 섹션만 보완했다.
