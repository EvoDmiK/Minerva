> **문서 상태: 진행 중 (초안 작성, 496건 평가 실행 및 DB Oracle 대조 진행 중; 최종 수치 수령 후 갱신 예정, 앱/DB/배포/Git/기존데이터셋/백로그상태 수정 없음)**

> 본 평가는 단순한 상위 API 상태 코드 확인에 그치지 않고, 결정적(deterministic) 계약 스코어러(Contract Scorer)를 통한 기대 조건 검증과 함께 실제 TEST 컨테이너 내부 DB의 조상 계통(ancestry) 및 형질(trait) 오라클과의 전수 대조(480건)를 연계 수행한다.  
> 첫 번째 시도에서 MLflow SDK의 최상위 `expectations` Null 값 제약(`MlflowException: The 'value' field must be specified`)으로 인한 하네스 중단이 발생했으나, 원본 데이터셋의 기대값을 불변 보존한 채 평가 DataFrame에서 `expectations={"contract": 원본expectations}`로 중첩 래핑하여 하네스를 정상화하고 496건 전체 재실행을 개시했다.

## 2. 해결 방안 및 평가 파이프라인 설계

### 1) 원본 데이터셋 보존 및 DataFrame 중첩 래핑
- 원본 Native 데이터셋(496건)의 expectations 스키마(`taxon`, `rank`, `conditions`, `outcome`)는 수정 없이 그대로 불변 유지함.
- `scripts/evaluate_graph_question_dataset.py`에서 `mlflow.genai.evaluate`로 전달하는 평가용 DataFrame 생성 시:
  ```python
  # 최상위 Null 제약을 우회하면서 내부 Null을 완벽히 보존
  eval_df["expectations"] = eval_df["expectations"].apply(lambda exp: {"contract": exp})
  ```
  - 최상위 키가 `"contract"` 1개로 단일화되고 그 값은 딕셔너리(`dict`, non-null)가 되므로 MLflow SDK의 `Expectation(name="contract", value={...})`가 정상 생성됨.
  - 스코어러 내부에서는 `expectations["contract"]`를 참조하여 원본의 `rank=None`, `taxon=None`을 그대로 보존하여 엄격한 일치성 검증을 수행함.

### 2) 2단계 엄격 검증 체계
1. **Contract Scorer (결정적 계약 스코어러)**:
   - `predict_fn`을 통해 반환된 응답과 기대값(`contract`)을 1:1 비교.
   - `taxon`, `rank`, `conditions` 일치 여부 및 `outcome`(`query`, `empty`, `hold`, `insufficient`) 판정.
2. **DB Oracle 재대조 (`verify_graph_question_evaluation_evidence.py`)**:
   - 496건 중 `query`/`empty` 478건과 아종 직접 부족 2건 등 총 **480건**에 대해 실제 TEST 컨테이너(`robingraph-api-test`) 내부 DB에서 직접 조상 계통 및 형질을 재계산하여 전수 대조.
   - 반환 종수, `coverage`(`scoped`, `evaluable`, `matched`), 페이지네이션(`has_more`), 조건 일치성 검증.

### 3) 예외 케이스(18건) 정밀 감사 기준
- **보류 (`hold`, 14건)**:
  - `disposition == 'clarify'`이거나 실행된 `conditions`가 없는 정상 보류인지 확인.
  - 특히 **`IT-043`과 `IT-044`는 조건 추출은 되었으나 `taxon_resolution="ambiguous"`로 인해 의도적으로 실행되지 않은 정상 보류(abstain)**이므로, '조건 존재 = 실행 실패'로 오판하지 않도록 명문화.
- **자료 부족 (`insufficient`, 4건)**:
  - 나팔새류(`CT-016`) 등 미해소/동음이의 사유 확인.
  - 아종 질의의 `evaluable == 0` 및 계급 `subspecies` 사유 확인.

### 4) 지연 시간 및 라우팅 메타데이터 기록
- **지연 시간 표기 원칙**:
  - 앱이 재시작되지 않고 이전 평가로 이미 가열(warm)된 상태이므로, 'Cold prototype load'로 단정하지 않고 **`first_request`와 `subsequent_request (p50/p95)`로만 분리 기록**.
- **라우팅 추적 원칙**:
  - API 응답 내 `selected_intent`, `route_method`, `result.kind` 메타데이터는 보존.
  - 단, MLflow `graph_intent` 스팬/상태에 대한 독립 감사는 미실시되었으므로 **'fallback 발생 여부 확인 완료' 등으로 추정하지 않음**.
