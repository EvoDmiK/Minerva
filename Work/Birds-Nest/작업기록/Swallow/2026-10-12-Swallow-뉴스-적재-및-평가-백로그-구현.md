## 2. 워크플로우 및 DB 아키텍처 상세 사양

### 2.1 뉴스 브리핑 워크플로우 (`[Stock] Swallow`, 총 40개 노드, +3노드)
- **추가된 노드 (+3개)**: `활성 관심종목 조회`, `관심종목 뉴스 매핑`, `관심종목 뉴스 저장`.
- 기존 `Deduplicate & Parse`에서 최신 10건 외의 관심종목 언급 기사 최대 20건을 추가한다. `analysisScope='watchlist'` 추가분은 뉴스 저장만 하며 기존 모의매매·Discord 대상에서 제외한다.
- 저장소 export는 37→40노드다. 실제 운영 workflow 교체는 아직 하지 않았다. 기사 발행 시점의 시세 스냅샷을 뉴스 테이블에 새로 저장하는 변경은 아니다.
- **기사 복원 및 전달 로직 정정 (root 리뷰 보완 `a1c4cf9`)**:
  - `itemMatching` / `pairedItem` 구조를 적용하여 DB 저장 및 시세 조회 후에도 원본 기사 속성(URL, 제목, 언론사)이 유실되지 않도록 보존.
  - 신규 종목 `INSERT`가 0행(이미 존재하는 ticker)인 경우에도 downstream 처리를 위해 1행을 안전하게 리턴.
  - **본문 근거 필수화 및 메타데이터 가드 (`a1c4cf9`)**: LLM이 반환한 `direct` 종목도 실제 기사 본문 내 종목명 존재 근거를 필수로 요구하며, `publishedAt`이 null/빈값이거나 `impactScore`가 NaN/null/허용 범위 밖인 불량 데이터는 원천 제외.
  - LLM 및 기사 본문 종목명에 실제 근거한 direct/peer 종목만 `UNIQUE(watch_ticker, url)`로 적재하며, 기존 행 `ticker` 컬럼 upsert 정합성을 안전하게 보존.

### 2.2 모의투자 주문 멱등성 및 키 관리 (SW-002)
- **주문 고유 키**: `url|ticker|action` 포맷의 deterministic key 생성.
- **체결 상태별 키 소모 정책**:
  - **정상 체결 (`BOUGHT`, `SOLD`)**: 키를 소모하고 주문 이력에 기록. 재실행 시 `DUPLICATE` 상태를 반환하며 중복 주문을 차단.
  - **시세 부재 (`SKIPPED`) 및 런타임 예외**: 키를 소모하지 않거나 트랜잭션을 롤백하여 다음 유효 시점 실행 시 정상 재시도 가능.
- **하위 호환성**: 키가 제공되지 않는 기존 MCP 7/8인자 호출 시에는 기존 로직대로 키 없이 체결 허용.

### 2.3 데이터베이스 스키마 요구조건
- 마이그레이션: `mcp/swallow-mcp/migrations/001_paper_order_keys.sql`
- **의존성 주의사항**: 본 DDL은 기존 `public.companies` 및 `public.stock_watchlist` 마스터 테이블이 사전에 존재하는 환경을 전제로 작성되었으며, 빈 DB에 단독으로 실행 가능한 독립 완결 DDL이 아닙니다. 초기 fresh DB 스키마 첫 시도 시 기존 `companies` 마스터 부재로 실패했으나, 마스터 fixture 생성 후 스키마 및 contract 검증이 정상 통과되었습니다.

## 5. root 최종 통합 검증 및 정리

- 최종 입력 가드를 반영한 n8n-test 비활성 fixture에서 root가 직접 **18136/18137**을 실행했다. 둘 다 success이며 재실행 후 뉴스·거래·주문키는 각각 **3건으로 불변**이었다. 기존 티커·신규 INSERT·INSERT 0행 모두 원문 URL과 티커가 일치했다.
- 같은 격리 DB의 실제 적재 3건을 최종 Grafana 패널 SQL로 조회: 호재 2/악재 1, 상세 3건. 가격이 없으면 당시가격·변동률·적중률은 NULL이다. 별도 9기사 fixture **10개 쿼리**도 통과했다.
- root의 최종 Node 테스트 **47 pass**, DB 계약 SQL 통과, 실제 NAS 데이터 DB의 대시보드 SQL **21개 성공**. 외부 공급자·Gemini는 stub이므로 실연동 검증으로 간주하지 않는다.
