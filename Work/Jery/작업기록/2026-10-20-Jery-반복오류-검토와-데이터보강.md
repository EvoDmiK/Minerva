# 반복 오류 검토와 10개 도구 데이터 v2

사용자가 반복 오류와 정답 검토, 헷갈리는 도구 경계 사례 보강을 요청했다. 배치·시드 10회 Parent a29741cab715401ea4ae3fa25cbe3ea4는 완료됐으며 추가 파라미터 탐색 대신 데이터와 입력 명세를 점검했다.

## 관찰과 라벨 대조

선정 head의 validation 예측만 결합했다. 10개 run에서 20개 source_id가 각각 한 번씩 있어 총 200개 예측이고 그중 오류 80개다. 독립 사례는 200개가 아니라 검증 20개다. 10개 사례에서 한 번 이상 오류가 있었고 4개는 모든 실행에서 틀렸다. Test 예측은 오류 분석에 사용하지 않았다.

- Bases 뷰 조회: 10/10 실행에서 Dataview로 오선택.
- 과거 일별 종가 조회: 10/10 실행에서 현재가로 오선택.
- 한 종목 보유 여부: 10/10 실행에서 다른 도구로 오선택.
- 계좌 전체 평가손익 사례: 10/10 실행에서 주문/가격 이력으로 오선택.
- Frontmatter 수정 2건: 각각 9/10, 7/10 오류.
- 파일 이름 변경: 4/10 오류.

고정 카탈로그에는 vault.rename, edit.patch(frontmatter), bases.view가 있지만 기존 짧은 선택지 설명은 일부 기능을 생략했다. 이는 확인된 표현 품질 문제다. 실제 오류의 단일 원인이라고 단정하지 않는다. 카탈로그와 직접 충돌하는 기존 라벨은 확인하지 못했으며 label-inspection.json은 AI 대조 결과다. Human review 또는 execution 상태를 승격하지 않았다. 카탈로그가 정답의 유일성이나 실행 성공을 보장하는 것도 아니다.

## 데이터 보강

새 criteria 명세로 설명 누락을 보완하고 hermes-ten-tools-v2 / decision-export-v2로 구분했다. 최종 catalog는 hermes-ten-tools-2289142ab57a이다. Native 검사의 옵션당 24token 한도를 통과하도록 설명을 압축한 representation_version v2.1-native-budget을 사용한다.

180개 AI 작성 합성 train 사례(도구당 18개), 60개 신규 시나리오를 추가했다. 시나리오마다 직접 요청·표현 변형·맥락 해결형을 모두 train에 둔다. 기존 60개와 합쳐 240개, 도구당 24개다. review_status는 needs_human_review, execution_verified는 false다.

초기 초안의 Dataview 상태 문장 1건이 기존 validation 입력과 중복돼 자동 검사에 차단됐다. 그 family 전체를 폐기하고 별도 CALENDAR 질의로 교체했다. 정규화 중복·split 간 group 교집합·후보/정답·카탈로그 action 참조·출처 해시를 검사한다.

## 분리 검증과 비교 설계

description_control은 기존 train 60개에 새 설명만 적용하고 augmented는 같은 설명으로 train 240개를 사용한다. 두 profile의 validation/test 각 20개는 바이트 동일하다. 이전 v1의 state·gold·aliases·scenario·순서는 보존하되 설명·catalog provenance는 바뀌므로 이전 입력과 바이트 동일하지 않다. 기존 원본 데이터와 export는 덮어쓰지 않았다.

고정 seed3407, batch4, LR0.0003538647078409709, weight_decay0.05, smoothing0.05, warmup10, 같은 base를 사용한다. 대조군은 32에폭×15step, 보강군은 8에폭×60step으로 최대 optimizer budget을 480step으로 맞춘다. 조기 종료와 평가 주기는 달라 단일 시드 회귀 비교로 해석한다. Test로 튜닝하지 않는다.

이미 관찰된 검증 오류에서 얻은 기능 경계로 보강했으므로 validation-informed 합성 데이터다. 독립적인 실제 요청 평가나 실사용 개선 증거는 아니다.

## Native 재검사와 실제 실행

확장 설명 초안은 옵션당 24token 한도에서 6개 옵션이 잘려 사전검사에 실패했고 학습하지 않았다. 초안은 별도 native-draft 경로에 보존했다. 핵심 기능을 유지해 설명을 압축한 최종 기준은 catalog hermes-ten-tools-2289142ab57a, representation v2.1-native-budget이다. 두 profile 모두 skip·target/특징 불일치·잘림 0건, 최대 전체 입력 길이 289token을 통과했다.

[보강 학습 Parent 5f64008a](https://mlflow.dove-nest.com/#/experiments/47/runs/5f64008a2b974b7f87fab5088bafcf8a), [설명만 보완 Parent f7faeae2](https://mlflow.dove-nest.com/#/experiments/47/runs/f7faeae2708945d6b62f59e54a6f56ae)를 생성하고 회사 GPU supervisor PID 205389·205449로 시작했다. 같은 base·seed·batch·LR·정규화와 최대 480 optimizer step을 사용한다. 감사 입력·JSON·라벨 대조·합성 원문·criteria·notebook·native readiness를 두 Parent에 업로드한다. 최종 압축 명세 수정은 c15348e로 dev-codex에 커밋·푸시하고 서버에 반영했다.


## 학습 완료 후 관찰

두 모델의 GPU 학습은 끝났다. 보강군은 6에폭·360step, initial validation 60% → best trained/serving validation 65%(epoch3)였다. 설명만 보완한 대조군은 22에폭·330step, initial/best trained validation 60%로 serving은 초기 head를 유지했다. 양쪽 모두 frozen encoder 유지와 저장·재로딩 후 validation 예측 일치를 확인했다.

보강군과 대조군 차이는 검증 20개 중 한 문제이고, 이전 최고 validation 65%를 넘지 못했다. 반복 관찰된 회귀 자료의 단일 시드 결과이므로 실제 개선으로 주장하지 않는다. Test는 이 결론이나 추가 튜닝에 쓰지 않았다. 감사 관련 artifact 7개를 각 Parent에 업로드하고 SHA-256 read-back을 확인했다. 모델 artifact 업로드·최종화는 supervisor가 계속 처리 중이다.


## Parent–Child 구조 정정

사용자 지시에 따라 같은 비교의 조건을 Parent 두 개로 나눴던 구성을 정정했다. Canonical Parent는 5f64008a2b974b7f87fab5088bafcf8a, 이름은 laya-ten-tools-data-quality-comparison-20261020이다. 직접 Child는 description-only-train60(6145fe8c826a4fcea9f23fc525535aec)와 augmented-train240(5ee0cebebfbd465898abdd4b5f300a56) 두 개이며 모두 FINISHED다.

재학습 없이 parentRunId를 변경했고 params·metrics 동일성을 API로 확인했다. 모델은 기존 Child artifact에 그대로 있다. 각 조건의 데이터·plan·config·summary를 Parent conditions/{condition}/에 복사하고 SHA-256 read-back으로 검증했다. 빈 중복 Parent f7faeae2708945d6b62f59e54a6f56ae는 soft-delete로 보관했으며 기존 metadata/artifact는 보존했다. 현재 관계는 Parent summary.json·comparison-plan.json, 변경 전후 snapshot은 comparison/before.json·after.json을 따른다. 이전 tracking 디렉터리는 통합 전 실행 이력으로 보존하고 재개하지 않는다.

다음 권장 과제는 이 프로젝트의 학습·튜닝에 사용하지 않은 실제 요청을 모아 도구별 약 10개씩 100개 내외의 고정 평가셋을 만들고 정답을 검토하는 것이다. 이 평가셋 구축은 아직 시작하지 않았다. 동일한 새 평가에서 보강 전후 모델을 비교한 뒤 인코더 일부 학습이나 모델 변경 필요성을 판단한다.
