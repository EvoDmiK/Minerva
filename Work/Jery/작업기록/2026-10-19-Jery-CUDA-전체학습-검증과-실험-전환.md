# CUDA 전체 학습 검증과 다음 실험 전환

RTX 5070 Ti 회사 서버에서 전체 데이터 한 에폭을 학습·평가·저장하고, 새 모델 인스턴스 복원과 native optimizer checkpoint 재개를 확인했다. 기존 Mac Hyperopt 실험은 유지한다.

## 실제 시간과 정확도

| 구간 | 시간 |
|---|---:|
| CUDA optimizer 계산 합계 | 243.61초 |
| CUDA 한 에폭 학습 + 검증 + native checkpoint | 271.85초 (4분 32초) |
| CUDA CLI 전체: 로드·인코딩·baseline·학습·평가·저장·복원·최종 test | 356.28초 (5분 56초) |
| 이전 Mac 첫 에폭 학습·checkpoint·검증 | 1,149.71초 (19분 10초) |

해당 구성의 에폭 학습·검증은 약 4.2배 빨랐다. backend precision, micro batch/누적 방식과 학습률이 달라 하드웨어 단독 비교는 아니다. 서버에서는 기존 IsaacLab·vision 작업을 유지했다. 다른 작업의 처리량 변화는 측정하지 않았다. 최대 PyTorch CUDA 할당은 1.359GiB였다.

정확도 개선은 없었다. baseline validation 16.13% → 학습 한 에폭 후 3.63%로 하락해 정책대로 epoch 0 head를 선택·복원했다. 최종 validation 16.13%, test 15.04%는 복원한 초기 head의 결과다. 실제 한 에폭 학습 head는 MLflow의 `model/last-trained/`로 구분해 올렸다.

## 구성과 검증

- 경로: `/home/persona-ai/git/Jery-cuda`, Python `/home/persona-ai/envs/jery-cuda/bin/python`.
- 모델: 같은 Laya multilingual base, FP16 frozen encoder / FP32 routing head 14,770,945개 / BF16 autocast.
- 데이터: 합성 미검토 `mcp-routing-v2`, 계약 `decision-export-v1`, 카탈로그 `hermes-mcp-57e701d87790`.
- 원본 사례 668/248/246개, exhaustive window 4,172/1,592/1,577개. 학습의 모든 원래 window를 유지한 균형 샘플링 8,530개, 2,133 step/epoch.
- micro batch 4 / accumulation 1 / eval batch 4. CUDA allocator 한도 30%는 메모리 한도이며 연산 점유율 제한이 아니다.
- 모든 split 토큰 절단 0. 특징은 state·questions만 사용하며 blind encoder와 native dataset builder의 특징을 전수 비교했다.
- encoder 전체 파라미터 해시 불변, head 갱신, 새 모델 인스턴스에서 validation 확률 차이 0 및 동일한 case 예측 확인.
- checkpoint의 trainer·Adam optimizer step을 2,133→2,134로 재개하고, 원본 checkpoint 모든 파일 해시 보존 확인. 저장 학습률 0에서 한 스텝을 이어 가는 호환성 확인이며 성능 개선 검사가 아니다.

## MLflow와 다음 실험

Experiment 이름은 `Jery`를 유지하고 Parent를 분리했다.

- [서버 한 에폭 검증 Parent](https://mlflow.dove-nest.com/#/experiments/47/runs/8512d92300244b98a92ed07f0f64f4c2), Child `b4b307c8271f4e65beaa10e8f89df97f`: 완료.
- [기존 Mac Parent](https://mlflow.dove-nest.com/#/experiments/47/runs/9325d1ca84944fe281f94b519c59f305): 계속 실행.
- [다음 CUDA Hyperopt Parent](https://mlflow.dove-nest.com/#/experiments/47/runs/29552487a8a94b10ad942d9bbc331953): 5회 TPE 탐색을 준비했다. 서버 검증 통과 후 Mac Parent가 `FINISHED`일 때 시작하도록 대기 실행을 연결한다. Mac이 실패·중단되면 자동 시작하지 않는다.

다음 실험은 최대 64에폭/trial, 40/40/10/10 균형, validation case accuracy 기준, epoch 0 포함, patience 5·min_delta 0.004를 유지한다. readiness 점수를 Hyperopt에 섞지 않는다. Child params 4개·metrics 7개만 기록하고, 나머지는 JSON artifact와 모델 safetensors로 저장한다. 데이터와 코드도 Parent/Child artifact에 기록하고 업로드 뒤 SHA-256을 재조회한다.

코드는 `src/jery/model/laya_cuda.py`, 설정 `configs/model/laya-cuda-20261019.json`, 재현·상태 확인은 `docs/model/laya-cuda-full-20261019.md`에 있다. `scripts/run_laya_full_experiment.py --wait-for-run`으로 순서를 지키며, `scripts/check_laya_cuda_resume.py`는 원본 checkpoint를 변경하지 않는 재개 확인용이다.

## 완료·재개 검증과 배포

완료된 readiness 파일을 별도 경로로 복사해 실제 `--resume`도 확인했다. 이미 한 에폭을 마친 경우 optimizer step을 추가하지 않고 후처리만 재개했으며, 기존 test 캐시와 동일한 최종 head를 유지했다. 실제 마지막 학습 head의 SHA-256도 native checkpoint에서 추출한 원본과 일치했다. 전체 테스트 112개와 v1/v2 검증을 통과했다.

`dev-codex`의 [`1c0011f`](https://github.com/EvoDmiK/Jery/commit/1c0011ff4ad49a67d522a68a3d3f71550b0ea303)을 커밋·푸시하고 서버 checkout에도 fast-forward 반영했다. 로컬과 서버 Git 작업 트리는 깨끗하다. 다음 CUDA Hyperopt supervisor PID는 `168044`이며 `--wait-for-run 9325d1ca84944fe281f94b519c59f305`로 시작했다. 실제 대기 상태 확인은 후속 기록에 남긴다.

실제 확인 결과 다음 CUDA Parent는 `waiting_for_upstream`, supervisor PID `168044` 생존, Child 0개였다. 선행 Mac Parent의 MLflow 상태는 `RUNNING`이다. 대기 중 서버 GPU에는 기존 IsaacLab PID `123090`과 vision PID `126024`만 남아 있다. 검증 증거 JSON을 다음 CUDA Parent의 `readiness/queue-verification.json`에 업로드하고 SHA-256을 재조회했다. readiness Parent의 `readiness/completed-checkpoint-replay.json`에도 완료 checkpoint 재개 결과를 보관했다.

## 사용자 요청으로 CUDA 즉시 시작

사용자가 “아니야 그냥 CUDA도 바로 돌려줘”라고 요청해 Mac 완료 대기를 해제했다. 대기 중이던 supervisor PID `168044`만 정상 종료하고, 같은 CUDA Parent를 `--wait-for-run` 없이 재시작했다. 새 supervisor PID `171196`, 첫 Child `34b877ee4f164c06ba40ea87691c3dc0`이며 상태는 `running`이다. Mac의 5번째 trial은 그대로 진행한다.

기존 5회 TPE·최대 64에폭·검증 콜백과 데이터 구성은 유지한다. 사용자 지시와 대기 해제 이력은 CUDA Parent의 `control/immediate-start-override.json`에 저장하고 SHA-256을 재조회했다. 이전 절의 Mac 완료 대기 기록은 과거 상태이며, 현재는 두 장비에서 독립적으로 실행한다.

첫 CUDA trial의 실제 optimizer step 증가를 확인했다(최초 확인 3 step, GPU PID `171268`, 사용량 약 1,666MiB). 실행 정책 문서를 `dev-codex`의 `1c347a0`로 커밋·푸시했다. 코드·학습 하이퍼파라미터 변경 없이 실행 대기 조건만 해제했다.
