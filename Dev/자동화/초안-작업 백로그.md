- **배경**: 현재 API는 FastAPI/Pydantic + uvicorn이며 검색(retrieval)·수집(ingest)은 별도 Python 모듈이다. `src/robingraph/api/app.py`(1,624줄)에 라우트와 채팅 오케스트레이션·응답 매핑이 함께 있고, 내부 수집 API는 `ingest_router.py`의 `/internal/v1/ingest`(내부 Bearer)다. PostgreSQL은 `ingest/migrations/0001~0004_*.sql`과 `_schema_migration`으로 자체 관리한다. 아래 분석은 2026-10-20 main-2 `07b1cf8` 읽기 전용 **예비 분석**이며 전체 전환 설계를 검증한 결과가 아니다.
- **목적**: 기존 API URL과 응답·오류 계약을 유지한 채 웹 계층을 Django + DRF로 전환하고, 조류 근거·데이터와 Neo4j 검색 로직을 재사용하는 프레임워크 독립 서비스 계층을 만든다. **성능 향상은 목표나 약속이 아니다.**
- **단계별 하위 작업**:
  1. 계약 고정: 현재 엔드포인트 전수와 요청·응답·오류 계약(OpenAPI 스냅샷·기존 테스트)을 기준선으로 고정한다. 대상 예: `POST /v1/answers`, `/v1/chat`, `/v1/search`, `GET /v1/observations`, `/v1/taxa/lineage`, `/v1/taxa/{name-relations,related,similar,ecological-related,subspecies,profile}`, `/health`, `/internal/v1/ingest/*`.
  2. 서비스 추출: `app.py`의 채팅 오케스트레이션·응답 매핑을 프레임워크 독립 서비스로 추출한다(먼저 FastAPI에서 동작 유지).
  3. Django + DRF 계층 추가: 설정과 URL·View·Serializer. Serializer는 기존 Pydantic 계약과 같은 JSON을 낸다.
  4. 데이터 계층 유지: Neo4j 드라이버·검색·벡터 코드와 조류 근거·데이터를 그대로 사용한다. 기존 PG SQL·스키마는 초기에 그대로 두고 Django auth/admin 등 Django 자체 마이그레이션과 명시적으로 분리한다.
  5. 이전 순서: 조회(query) → 채팅(chat) → 수집(ingest, 내부 Bearer 유지).
  6. 정적 UI 재사용: `api/static/`과 `/`, `/chat`, `/birds`, `/favicon.ico`, `/static/...` 경로 유지.
  7. 실행·배포 갱신: 테스트(`TestClient`/`fastapi` 참조 17개 파일 포함), Dockerfile·HEALTHCHECK, CLI `serve`/`serve-fixture`, Jenkins 파이프라인, ASGI/WSGI 런타임.
