# 홈 AI 인프라 문서 검토

## 결론

역할 분담 방향은 타당하다. 목표 구성과 실제 운영 기록의 기준이 어긋나 있어, 신규 DB·분산 처리·장비 추가보다 **현황 동기화와 복구 가능성 확인이 먼저**다.

이번 작업은 Obsidian MCP로 원문을 읽고 비교한 문서 검토다. 문서에 기록된 서버 점검을 새로 실행한 것이 아니다. 원본 문서와 실서비스 설정은 수정하지 않았다. 최종 검토 지적을 원문과 대조해 반영했다. `completed`는 문서 검토 완료를 뜻하며 서버 정상·보안 설정·복원 검증 완료를 뜻하지 않는다.

## 유지할 설계

- AI·애플리케이션·저장 역할 분리와 증설 전 병목 측정.
- 장비별 RAM 독립성, macOS 자동 스왑과 메모리 압박 중심 관리.
- RAID와 별도 백업 구분.
- 실행 상태와 기능 정상 여부 구분.
- macOS 실제 호스트 지표와 OrbStack Linux·컨테이너 지표 구분.
- 초기 메모리 예산과 실측을 구분한 표현.

## 주요 검토 결과

### 1. 목표와 현황 문서의 상태 동기화

근거: 구성 §2·4·10·11·13, 운영 현황 「모니터링 연결 상태」「구성 계획과 실제 운영의 차이」「자원 및 운영 점검 메모」.

구성에는 Prometheus·exporter 연동과 HDD 구성이 미확인으로 남아 있지만 현황에는 양측 Prometheus, Mac→NAS federation, macOS 직접 수집기, HDD RAID1 점검 기록이 있다. Neo4j도 목표 Mac #2 배치와 달리 NAS 운영·Mac #1 테스트로 기록돼 있다.

구성을 목표 설계, 현황을 점검 시점의 실제 상태로 구분하고 상호 링크한다. 설치·연동 항목은 확인 날짜·출처와 함께 갱신하되 복원·재부팅·전체 기능 정상까지 검증 완료로 확대하지 않는다. Mac #2는 미점검이지 빈 장비가 아니며, 계획과 다른 배치만으로 이전을 권하지 않는다.

### 2. 단일 SSD 주요 DB의 복구 가능성 확인 — P1

근거: 운영 현황 「데이터베이스 확인 결과」「자원 및 운영 점검 메모」.

주요 DB는 단일 SSD이며 HDD RAID1과 별개다. pgBackWeb 실행은 확인됐지만 최근 백업 성공·복원이 미검증이다. **백업이 없는 것으로 확정된 것이 아니라 복구 가능성이 확인되지 않은 상태**다.

개선 제안: PostgreSQL 외 Neo4j, n8n 구성, MLflow 메타데이터·실험 산출물, Vault·OpenViking의 원본 및 재생성 가능 자료를 구분한다. 운영 SSD 외부 보관, 보존 기간, 필요한 설정·암호화 키의 별도 안전 보관, 허용 데이터 손실 시간(RPO), 목표 복구 시간(RTO), 격리 환경 복원 결과를 확인한다. 같은 NAS 안의 사본과 별도 장치·오프사이트 사본은 장애 범위가 다르므로 중요 자료의 보관 위치를 구분한다.

n8n 암호화 키는 적용 방식에 따른 확인 항목이며 이번에 저장 상태를 점검한 결과가 아니다. 비밀값을 노트에 기록하지 않는다.

### 3. 관리·공개 접속 경로를 서비스별로 명시 — P1 확인 과제

근거: 구성 §7, 관련 인증서·접속 경로 기록 §1~3.

과거 결정: 관련 기록은 Cloudflare 프록시·Origin 인증서를 유지하고 Split DNS/직접 도메인 경로를 제거한 결정을 설명한다. 이는 Tailscale 전체 제거를 뜻하지 않는다.

현재 미확인: ACL·방화벽·외부 노출·Full(strict) 적용 여부. 관련 기록의 strict는 권장이며 원본 접근 제한은 강화 과제로 남아 있다. 당시 기록만으로 현재 미적용이나 실제 취약성을 단정하지 않는다.

개선 제안: 기존 결정을 무조건 되돌리지 않고 서비스별 `공개 여부 | 접속 경로 | 앱 인증 | TLS 종료 | 원본 접근 제한`을 기록한다. 관리용 Tailscale과 필요한 공개 경로는 공존할 수 있다. Origin 인증서의 긴 유효기간은 갱신 빈도를 줄일 뿐, 키 관리·원본 연결·TLS 설정·우회 접근 위험을 없애지 않는다.

### 4. Grafana와 n8n DB 공유 경계 검토 — 구조 개선은 P2

근거: 운영 현황 「데이터베이스 확인 결과」.

Grafana가 n8n 논리 DB를 사용하도록 설정됐다고 기록되어 있다. 같은 PostgreSQL 인스턴스 공유와 같은 DB 공유를 구분해야 한다. 실제 권한 범위·충돌·침해 발생은 이번에 확인하지 않았다.

개선 제안: 접근 통제 확인의 일부로 실제 DB명·schema·role·권한을 확인하고, Grafana 전용 DB·계정과 서비스별 최소 권한·백업·복구 경계를 검토한다. 분리 자체는 기본 P2이며 접근 통제 결함이 발견되면 긴급도를 높인다. 이전은 별도 승인·검증 작업이다.

### 5. 자원 부족은 단일 수치보다 추이로 판정 — P2

근거: 구성 §5, 운영 현황 「자원 및 운영 점검 메모」「실제 Mac 하드웨어와 Docker 지표의 구분」.

NAS available 약 5.2GiB와 swap 약 3GiB는 단일 시점이며 짧은 구간에 추가 swap IO가 없었다. 이것만으로 상시 부족이나 즉시 증설 필요를 확정하지 않는다.

Mac 테스트 Neo4j 약 5.17GiB와 초기 계획 `2~4GB부터`는 서로 다른 조건이다. 해당 측정값을 다른 호스트의 운영 메모리 제한으로 바로 옮기지 않는다. 호스트 압박·swap IO·VM 예산·컨테이너 제한 대비 사용률·재시작·OOM 기록을 구분해 관찰한다. 현재 OOMKilled=false는 과거 OOM 부재를 보장하지 않는다.

로컬 LLM·학습 운영 여부는 미확인이다. 실제 도입 계획이 확정된 경우에만 실행 위치와 다른 서비스와의 동시 부하를 후속 검토한다.

### 6. 기존 모니터링과 기동·복구를 기능적으로 검증 — 새 제품보다 우선

근거: 운영 현황 「모니터링 연결 상태」「자원 및 운영 점검 메모」.

원문은 targets up, Grafana DB 연결, 주요 대상 restart 정책을 확인했지만 전체 기능 정상과 전체 재부팅 복구는 보장하지 않는다고 명시한다.

개선 제안: Loki 등 추가 제품보다 필수 호스트·컨테이너 지표가 실제로 수집되고 대시보드에서 조회되는지, 수집 중단·서비스 장애 시 알림이 전달되는지, 재부팅 후 네트워크·스토리지·DB·의존 서비스가 올바른 순서로 복구되는지 검증 계획을 먼저 세운다. 변경·장애 유발·재부팅 시험은 별도 승인과 안전한 범위를 필요로 하며 이번에 실행하지 않았다.

### 7. 추가 도구와 장비는 실제 요구에 연결 — P3

근거: 구성 §9·12, 운영 현황의 pgvector 확인 결과.

- 유지: 기존 PostgreSQL·Neo4j·n8n·Grafana/Prometheus, 사용 중인 Hermes/OpenViking과 관리·백업 도구. 의존성을 확인하지 않고 삭제하지 않는다.
- 조건부: 검색 품질·데이터 위치·규모·지연시간 요구를 먼저 확인하고 기존 Neo4j 검색과 pgvector·Qdrant 등 후보를 비교한다. 기존 도구만으로 충분하다는 판정은 아직 하지 않았다.
- pgvector 범위: B 점검 당시 TimescaleDB에는 설치 파일이 있었지만 점검 DB에서는 미활성이었다. 일반 PostgreSQL 두 인스턴스에서는 설치 파일이 확인되지 않았다. 그 밖의 DB·Mac #2 상태는 미확인이다. 모든 호스트에서 미구축이라고 확대하지 않는다.
- 보류: 규모·기능 요구 없는 Milvus·Ray. Celery는 Django 비동기 작업 큐 요구가 생길 때 검토한다. n8n과 Celery는 무조건 대체 관계가 아니다.
- 선택: Loki는 기존 모니터링 기능 확인 후 로그 기반 분석 필요와 수집·보존·디스크 한도를 정한 뒤 도입한다.
- 재평가: 4베이 NAS·UPS 순위는 용량과 전원·복구 위험을 확인해 정한다. UPS는 백업을 대체하지 않는다.

## 추가할 최소 운영 정보

공개 요약과 접근 제한된 복구 런북을 분리한다. 내부 복구용 운영표:

`현재 호스트 | prod/test | 기능 확인 상태·시각 | 배포 구성 참조 | 데이터 볼륨 참조 | 의존성 | 백업·복원 결과 | 재시작·복구 절차`

공개 요약에서 주소·포트·계정·절대 경로를 제외하는 방침과 별개로, 접근 제한 런북은 필요한 설정 관리처를 참조해야 한다. 비밀값 자체를 복제할 필요는 없다.

운영 현황 서두의 NAS 컨테이너 개수와 표 목록도 대조할 필요가 있다. 독립 행수 계산은 승인 제한으로 실행되지 않아 검증 완료 항목에 포함하지 않는다.

## 다음 순서

문서에서는 목표/현재/미확인 상태와 링크를 먼저 정리한다. 실운영 후속 검증은 아래 순서를 권한다.

1. 주요 데이터 백업 범위·독립 보관·실제 복원 결과 확인.
2. 관리 UI·DB·공개 API의 현재 접속·인증·원본 제한 확인.
3. Mac #2 현황, 자원 추이, 필수 지표·대시보드·알림 및 재부팅·의존 서비스 복구 검증.
4. 확인된 요구에 따라 DB 분리·벡터 DB·작업 큐·로그 시스템·장비 추가 결정.

이 순서는 권고이며 해당 실행이나 일정 생성을 승인한 것이 아니다.

## 검증 한계

라이브 서버·DB·컨테이너·ACL·인증서·백업·재부팅 시험은 이번에 실행하지 않았다. 일부 보충 공식 문서 조회는 실패/잘림이 있었고 보충 코드 실행도 승인 대기로 차단됐다. 따라서 해당 공식 지원 범위를 이번에 검증했다고 주장하지 않는다.
