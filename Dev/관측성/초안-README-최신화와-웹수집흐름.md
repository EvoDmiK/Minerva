## 4. 검증 근거 및 트러블슈팅

사용자가 README 최신화와 변경 내용의 Git push를 요청했다. 기존 기능·검증 시점 설명에 웹 화면·자료 준비·새소리의 단계별 흐름을 보완하고 현재 백로그 진입점을 추가했다. 이 기록은 README 설명의 변경과 검증을 다루며 앱 기능 구현이나 운영 상태의 새 검증을 의미하지 않는다.

후속에서는 Mermaid 다이어그램 3개, 자료별 역할 표, 새소리 수집·검토·공개의 상태 표를 추가했다. 운영 수집과 TEST 검토 기능·도감 재생을 구분하고 HippoRAG/PPR 미구현과 사람 검토·운영 승인 대기를 유지했다. 앞선 README 최신화 기록은 아래 원문 이력으로 보존했다. root가 문서 diff·링크·Mermaid 구조 검토 및 사용자 승인 범위의 `dev-codex` commit/push를 담당한다.

| 구분 | 변경 사항 | 상세 내용 |
|---|---|---|
| 원인 규명 / 요구사항 | 웹 화면과 수집 과정 설명 부족 | 현재 기능·데이터·새소리 단계와 남은 작업을 함께 읽을 진입점 필요 |
| 설계 및 해결 방안 | 기존 구현·검증 기록으로 흐름 설명 | 웹·자료 준비·음원 단계를 Mermaid 3개와 표로 정리 |
| 코드 / 설정 수정 | 앱·설정 변경 없음 | README 및 작업 문서만 수정 |
| 실서비스 배포 | 미실행 | TEST·운영 배포, 재시작, DB 쓰기 없음 |
| 검증 및 테스트 | 문서 근거 대조·root 구조/링크 검토 | 자동화 앱 테스트·실제 DB/API·브라우저 검증 미실행 |
| 형상 관리 | dev-codex, 사용자 push 요청 | 문서 작성 시점 commit/push 전; 실행 결과는 root 증거 수령 후 Obsidian 후속 기록 |

기존 README에는 기능과 설치·환경·검증 안내가 있었지만 사용자가 채팅·탐색기·도감에서 무엇을 보고, 그 자료가 어떻게 준비되는지 한눈에 이어 읽기 어려웠다. 새소리는 운영 수집 실행기와 TEST 검토 화면·기록 저장·도감 재생이 서로 다른 단계다. 수집을 공개 승인으로 읽거나 저장된 검증 기록을 오늘의 서비스 실시간 상태로 오해하지 않도록 구분했다.

- 채팅·탐색기·도감 → API → 결과·출처·후속 조회·피드백 흐름을 첫 다이어그램으로 정리했다.
- 외부·검토 자료 → 로더 → 버전·출처·라이선스·종 연결 검증 → PostgreSQL/Neo4j → 웹 조회 흐름과 필요 시 사진·설명 캐시를 두 번째 다이어그램에 표시했다. 모든 자료가 매일 자동 갱신된다는 주장은 하지 않는다.
- Commons 후보 → 비공개 보관 → 인증된 검토 → 별도 사람 검토·공개 흐름은 세 번째 다이어그램으로 분리했다.
- 기존 구현·기록의 범위 설명이며 새로운 수집·자동 승인·공개를 실행하지 않는다. 단일 조건 추가 후속 질문과 semantic 일반화 미완료, 문헌 PPR 미구현을 유지했다.
